# 설계 결정과 근거

챗봇을 만들면서 고른 모델과 조정한 값, 그렇게 정한 근거를 남긴다.
측정값은 `scripts/eval_retrieval.py`로 다시 만들 수 있다. 데이터나 모델, 값을 바꾸면 이 문서의 표도 함께 고친다.

```bash
.venv/bin/python scripts/build_embeddings.py   # data/를 바꿨으면 임베딩 파일부터 다시 만듦
.venv/bin/python scripts/eval_retrieval.py     # 1장, 3장, 4장의 수치를 다시 잼
```

측정 환경: 2026-11-17, Apple Silicon(MPS), 데이터는 홈페이지 안내 308개, 규정 9,131개, 연락처 620개 조각.

## 1. 임베딩 모델: `dragonkue/multilingual-e5-small-ko`

| 후보 | 크기 | 벡터 | 결과 |
|---|---|---|---|
| Gemini `gemini-embedding-001` | API | 문서당 1개(768차원로 축소) | 제외. 운영 키가 무료 등급이라 분당 3만 토큰 한도에 걸림. 첫 색인에 약 1시간 반, 실제로 100개 묶음 요청이 429로 계속 실패함 |
| `BAAI/bge-m3` | 568M | 문서당 1개(1024차원) | 제외. 운영 노드(t4g.medium, 4GB를 BE, FE와 나눠 씀)에 모델을 올려 두기에 큼 |
| `nlpai-lab/KURE-v2` | 149M | 토큰마다 1개(128차원, MaxSim) | 보류. 한국어 검색 품질이 가장 좋음(MTEB kor 검색 nDCG@10 평균 0.816, 모델 카드). 다만 토큰마다 벡터를 저장해 임베딩 파일이 커지고, CPU에서 문서 하나에 0.88초, 메모리 약 700MB(로컬 실측) |
| **`dragonkue/multilingual-e5-small-ko`** | 118M | 문서당 1개(384차원) | **선택.** 한국어 질문과 문서 쌍으로 추가 학습한 e5-small. 전체 임베딩 156초(MPS), 파일 10.6MB라 저장소에 커밋해 운영으로 보낼 수 있음 |

- 문서에는 `passage: `, 질문에는 `query: `를 붙인다. e5 계열이 학습한 형식이라 붙이지 않으면 성능이 떨어진다.
- 벡터는 정규화하고 코사인 유사도(내적)로 비교한다.
- 임베딩 파일 `data/embeddings-multilingual-e5-small-ko.npz`는 로컬에서 미리 계산해 커밋한다. 운영 파드는 읽기만 하고, 질문 한 문장만 실행 중에 임베딩한다.
- 품질이 부족하면 KURE-v2를 다시 검토한다(평가 세트로 비교).

## 2. 조각(chunk)과 검색용 창(window)

| 값 | 설정 | 근거 |
|---|---|---|
| 답변용 조각 | 의미 단위(조문, 페이지 탭, 연락처 한 행), 1,500자를 넘으면 줄 단위로 나눔 | 절차, 서류, 문의처가 한 조각에 함께 있어야 답이 끊기지 않음. 조각마다 메뉴 경로와 문의처 머리줄, 표 머리줄을 다시 붙임(`data/README.md`) |
| 검색용 창 `WINDOW_CHARS` | 550자 | 모델 입력 한도가 512토큰. 1,500자 조각을 그대로 넣으면 뒷부분이 잘림 |
| 창 점수 | 조각 점수 = 그 조각에 속한 창 중 가장 높은 유사도 | 조각 뒷부분에만 있는 내용으로 찾아도 학생에게는 조각 전체를 근거로 줌 |

512토큰 초과 조각(조각 그대로 임베딩할 때)

| 종류 | 조각 | 512토큰 초과 | 최대 |
|---|---|---|---|
| 홈페이지 안내 | 308 | 240 (78%) | 1,002토큰 |
| 규정 | 9,131 | 306 | 1,104토큰 |
| 연락처 | 620 | 0 | 67토큰 |

- 한국어 글자당 토큰: 중앙값 0.62, 상위 5% 0.72, 최대 0.86. 550자 × 0.86 = 473토큰에 접두사와 머리줄을 더해도 512토큰 안에 든다.
- 결과: 창 11,572개, 가장 긴 창 411토큰, 512토큰 초과 0개.

## 3. 혼합 검색

| 값 | 설정 | 근거 |
|---|---|---|
| 키워드 검색 | 띄어쓰기를 뺀 2글자 단위 BM25, `k1=1.2`, `b=0.75` | 형태소 분석기 없이 부서명, 업무명을 잡음. k1, b는 BM25 표준값 |
| 제목 가중 | 키워드 색인에 제목(메뉴 경로, 조문 제목)을 한 번 더 넣음 | 메뉴 이름과 조문 제목이 본문보다 질문과 잘 맞음 |
| 합치는 방식 | RRF(순위 역수 합), `RRF_K=60` | 의미 점수와 BM25 점수는 단위가 달라 순위로 합침. 60은 RRF 논문과 일반 구현의 기본값 |
| 키워드 비중 `KEYWORD_WEIGHT` | 0.2 | 아래 표 |

평가 세트 `eval/questions.jsonl` 31개(일상 표현 25개 + 고유명사, 부서명 6개). 정답 홈페이지 페이지의 순위

| 키워드 비중 | hit@1 | hit@4 | MRR | 4위 밖 |
|---|---|---|---|---|
| 0(의미 검색만) | 0.90 | 1.00 | 0.944 | 없음 |
| **0.2** | **0.94** | **1.00** | **0.954** | 없음 |
| 0.3 | 0.87 | 0.97 | 0.926 | 와이파이 |
| 0.5 | 0.87 | 0.97 | 0.922 | 와이파이 |
| 1.0(같은 비중) | 0.87 | 0.94 | 0.912 | 와이파이, 졸업 학점 |
| 키워드 검색만 | 0.71 | 0.87 | 0.80 | |

- 키워드는 "ISIC", "certpia", 부서명처럼 고유명사가 들어간 질문의 순위를 올린다.
- 비중이 크면 "와이파이"(질문)와 "무선랜"(페이지)처럼 표현이 다른 질문이 밀린다. 같은 비중일 때 의미 검색 2위가 14위까지 떨어졌다.
- 질문 31개로 정한 값이다. 평가 세트를 늘리면 다시 잰다.

## 4. 근거 판정 기준값 `GROUND_MIN_SIMILARITY = 0.42`

홈페이지 안내나 규정 중 가장 가까운 조각의 유사도가 이보다 낮으면 근거 부족으로 보고 `fallback`(확인되지 않음 + 문의처)으로 보낸다.

| 질문 | 최고 유사도 |
|---|---|
| 업무 질문 31개 | 최저 0.440(와이파이), 하위 10% 0.522, 중앙값 0.620 |
| 무관 질문 12개(`eval/off_topic.jsonl`) | 중앙값 0.354, 최고 0.524 |
| 무관 질문 중 일반 주제(날씨, 코드, 주식 등) | 0.30~0.43 |
| 무관 질문 중 학교 관련이지만 데이터에 답이 없는 것(동아리 회장, 교수 연구실, 학식) | 0.47~0.52 |

- 업무 질문과 "학교 관련이지만 답이 없는" 질문의 구간이 겹쳐 기준값 하나로 가를 수 없다.
- 그래서 기준값은 업무 질문 최저값(0.44) 아래인 0.42로 두어 정상 질문이 근거 부족으로 빠지지 않게 했다. 0.42에서 근거 부족으로 빠지는 업무 질문 0개, 기준값을 넘는 무관 질문 4개.
- 넘어온 무관 질문은 두 겹으로 막는다. `analyze`가 범위 밖 질문을 걸러 `refuse`로 보내고, 답변 프롬프트에 "자료에 답이 없으면 확인되지 않는다고 말하고 문의처를 안내한다" 규칙을 넣었다.

## 5. 프롬프트에 넣는 근거

| 값 | 설정 | 근거 |
|---|---|---|
| 종류별 개수 `QUOTA` | 홈페이지 4, 규정 3, 연락처 3 | 절차는 홈페이지 안내가 가장 직접적이라 가장 많이 넣음. 규정 수가 30배 많아 몫 없이 섞으면 규정이 자리를 차지함. 최대 조각 기준 약 1만 5천 자로 프롬프트가 커지지 않음. 측정 전 설계값이라 답변 평가 때 다시 봄 |
| 부칙 | 질문에 "부칙", "시행일", "경과조치"가 있을 때만 검색 | 부칙 2,154개는 대부분 시행일 조항이라 학생 질문에 거의 쓸모없음(`data/README.md`) |
| 연락처 보강 | 고른 홈페이지 안내의 담당부서로 전화번호부를 다시 찾아 최대 2개 | 홈페이지 담당부서 23종 중 전화번호부와 이름이 정확히 맞는 것 13종. "학생지원팀 교내장학 / 국가장학"처럼 업무 설명이 붙은 이름은 첫 단어로 맞춤. 다른 교정 페이지(성신교정 총무팀 등)는 성심 번호가 잘못 붙지 않게 맞추지 않음 |
| 교정 | 질문에 드러나지 않으면 성심 | 앱 사용자 대부분이 성심교정 학생. 연락처는 교정별로 거름 |
| 옛 부서명 | 대조표(37건)로 지금 부서명으로 바꿔 안내 | 홈페이지 본문에도 "학사지원팀" 같은 옛 이름이 남아 있음 |

## 6. 답변 모델과 대화

| 값 | 설정 | 근거 |
|---|---|---|
| 답변 모델 `CHAT_MODEL` | `gemini-3.5-flash-lite` | BE 공지 추출과 같은 모델, 같은 키. 분명함 판정과 짧은 안내 답변에 충분하고 비용이 낮음. 무료 등급 요청 한도를 BE와 나눠 쓰므로 운영 전 유료 등급 또는 별도 키 결정 필요 |
| 온도 | 질문 분석 0, 답변 0.2 | 분석은 같은 질문에 같은 판단이 나와야 함. 답변은 문장만 자연스럽게, 사실은 자료로 고정 |
| 질문 분석 출력 | JSON 모드 | 해석, 유형, 분명함, 대안을 코드에서 바로 씀. 문자열 "false"도 분명하지 않음으로 읽음 |
| 시간 제한 | 분석 20초, 답변 60초, 재시도 2번 | 학생이 끝없이 기다리지 않게 함 |
| 대안 해석 | 최대 2개 | 확인 버튼이 너무 많으면 고르기 어려움(설계 문서의 확인 화면) |
| 대화 기록 | 최근 6턴, 한 턴 2,000자, 질문 500자 | "그럼 복학은요?" 같은 이어지는 질문에 충분하고 프롬프트를 작게 유지 |
| 확인 대기 `PENDING_TTL` | 10분 | 학생이 확인 버튼을 누를 시간은 충분하고, 메모리에 질문을 오래 두지 않음 |

|---|---|---|

## 8. 운영 자원

로컬 Docker(ARM64)에서 이미지를 실행해 잰 값. 운영 노드(t4g.medium, Graviton2 2 vCPU)에서 다시 잰다.

| 항목 | 측정 | 정한 값과 근거 |
|---|---|---|
| 준비 시간 | 67초(torch, 모델, 키워드 색인 적재. 임베딩 계산 없음) | readiness probe는 `/readyz`, 초기 대기를 길게 둠 |
| 메모리 | 849MiB(서버 프로세스) | 파드 한도 1Gi 이상. 설계 문서 초안의 768Mi로는 부족 |
| 질문 임베딩 | 질문 하나 약 430ms(CPU) | Gemini 답변(수 초)보다 작아 그대로 둠 |
| 이미지 | 2.89GB(압축 전). torch CPU 688MB, 모델 466MB, scipy 등 약 250MB | GPU 빌드 torch는 받지 않음(`requirements.txt`의 CPU 전용 인덱스). 더 줄이려면 torch 대신 ONNX 런타임 검토 |
| 모델 파일 | 이미지 빌드 때 받아 넣음, 실행 중에는 `HF_HUB_OFFLINE=1` | 운영 파드가 Hugging Face에 접속하지 않음 |
| 임베딩 파일 | 10.6MB(float16), 저장소에 커밋 | 운영은 읽기만 하므로 캐시용 PVC가 필요 없음 |
